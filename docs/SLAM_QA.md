## 2. “你对 SLAM 的看法是什么？”

可以按下面的结构回答，避免只说“建图定位”：

### SLAM 不是单一算法

SLAM 至少包含：

1. 传感器和时间同步
2. 标定：雷达-IMU、雷达-底盘、相机-雷达
3. 前端：特征/点云匹配、运动估计
4. 后端：滤波/优化、IMU 预积分
5. 回环和地图一致性
6. 地图表示和更新
7. 动态环境和失效恢复
8. 实时性、算力、工程部署
9. 评价指标：ATE/RPE、地图一致性、重定位、鲁棒性

### 对 RM 场地的理解

RM 场地不是纯静态理想环境：

- 场地有金属、玻璃、重复结构
- 有其它机器人和移动道具
- 比赛节奏快，对实时性和恢复能力要求高
- 地图和世界模型可能有局部偏差

所以在 RM 场景里，SLAM/LIO 的重点不是只追求论文指标，而是：

```text
稳定 > 可解释 > 可恢复 > 精度
```

### 对 LIO 路线的看法

- FAST-LIO2：成熟、工程资料多，适合做 baseline
- Point-LIO：高频、剧烈运动下更有优势，参数和实现细节更敏感
- 多传感器融合：雷达 + IMU 是基础，后续可以加入轮速、相机、另一个雷达
- 评价不能只看点云“好不好看”，要看轨迹、重定位、地图一致性、CPU 占用和失败恢复

### 我目前的做法

- 先用 FAST-LIO / Point-LIO 跑通 2026 场地
- 用 TF、地图、Nav2 目标点验证整条链路
- 用 `lio_tune` 做参数对比
- 记录失败模式：TF 时间、IMU 单位、点云时间戳、地图/world 偏差

## 4. “Odin” 是什么，怎么接？

老师提到准备采购另一个雷达 `Odin`。  
在代码层面，不能直接把它当 MID-360S 用，需要先拿到：

- 具体型号和数据手册
- ROS 2 驱动和消息类型
- 点云格式（PointCloud2/CustomMsg）
- 时间戳单位和同步方式
- IMU 是否有、频率和单位
- 默认 IP、端口、供电
- 安装外参和 FOV

接入检查清单：

```text
1. 驱动能出 /livox/lidar 或对应点云话题
2. 时间戳和 /clock 一致
3. TF: base_link -> new_lidar_frame
4. 点云 frame_id 正确
5. 外参标定
6. 与 MID-360S 的时间同步
7. LIO 配置切换
8. 地图和 Nav2 验证
```

建议先向老师确认 Odin 的准确型号和资料，再决定是否替换 MID-360S 或做双雷达融合。
